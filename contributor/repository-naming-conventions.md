#  新增开源仓命名规范

## 1. 目的与范围

本规范规定 CANN 社区新增开源仓库的命名规则，覆盖：核心库、算子库、模型/Recipe、样例、工具、Benchmark、测试、文档等。

本规范旨在：
- 统一命名风格，降低用户检索与认知成本；
- 为新仓创建、重命名、命名冲突仲裁提供可操作依据。

## 2. 通用规则

- 仓名 **全部小写，**禁止大写字母，例外：已被业界广泛认知的专有缩写（如 `BLAS`、`FFT`）在代码仓介绍资料中可保留大小写，但 **仓名本身仍全小写**；
- 分隔符统一使用 **中划线** `-`，禁止下划线 `_`；
- 仅允许 `小写字母（a-z）、数字（0-9）、中划线(-)`，禁止中文、空格、特殊字符等；
- 仓名长度建议 3–40 字符，最长不超过 100 字符。

## 3. 核心库仓命名

核心库是 cann 的基础组件，命名遵循"短名优先、必要时加前缀"原则， 要求简短、好记、具备辨识度。

**命名格式**：

```
[cann-]<feature>
```

-  `feature` 表示核心库的功能用途，可以是1个单词或多个单词，多个单词之间使用中划线连接，必选；
-  `cann-` 前缀可选，表示cann项目，核心库默认使用不加前缀的名字，仅当名字与业界已有开源仓重名时增加前缀，以便用户快速区分。

**示例**：

| 仓库名    | 含义       |
| --------- | ---------- |
| `runtime` | 运行时库   |
| `hcomm`   | 通信基础库 |

## 4. 算子库仓命名

### 4.1 基础算子仓

**命名格式**：

```
ops-<feature>
```

- 以`ops-`作为前缀，表示算子仓，`feature` 表示算子的功能用途，必选，可以是1个单词或多个单词，多个单词之间使用中划线连接。

**示例**：

| 仓库名 | 含义 |
|--------|------|
| `ops-math` | 数学基础算子库 |
| `ops-transformer` | Transformer 算子库 |

### 4.2 行业算子仓

**命名格式**：

```
<industry>-ops[-<feature>]
```

- `industry` 表示算子所属的行业，可以是行业名称通用缩写，必选，例如：金融（fin）、电力（elec）、制造(mfg)、交通(tra)等；
- 中间`ops`表示算子仓，以中划线连接；
- `feature` 可选，表示算子的功能用途，强烈建议增加，可以是1个单词或多个单词，多个单词之间使用中划线连接。

**示例**：

| 仓库名 | 含义 |
|--------|------|
| `elec-ops-simulation` | 电力仿真求解算子库 |

## 6. 模型与算法完整实践仓（Recipe仓）命名

**命名格式**：

```
cann-recipes-<feature>
```

- `cann-recipes-`前缀表示cann项目的最佳完整实践或解决方案样例；
- `feature` 表示功能用途，必选，可以是1个单词或多个单词，多个单词之间使用中划线连接，要求简短、好记、具备辨识度。

**示例**：

| 仓库名               | 含义                                             |
| -------------------- | ------------------------------------------------ |
| `cann-recipes-infer` | cann推理业务的典型模型及加速算法优化的完整实践仓 |
| `cann-recipes-train` | cann训练业务的典型模型及加速算法优化的完整实践仓 |

## 7. 样例仓命名

### 7.1 特性样例

**命名格式**：

```
[cann-]<feature>-samples
```

- `cann-` 前缀可选，表示cann项目，建议在与业界其他开源仓重名时使用，以便用户快速区分；
- `feature` 表示样例的功能用途，必选，可以是1个单词或多个单词，多个单词之间使用中划线连接，要求简短、好记、具备辨识度；
- 统一采用 `-samples` 后缀。

**示例**：

| 仓库名 | 含义 |
|--------|------|
| `cann-ge-samples` | ge样例仓 |

### 7.2 行业样例

**命名格式**：

```
[cann-]<industry>[-<feature>]-samples
```

- `cann-` 可选，表示cann项目，建议在与业界其他开源仓重名时使用，以便用户快速区分；
- `industry` 表示所属的行业，可以是行业名称通用缩写，必选，例如：金融（fin）、电力（elec）、制造(mfg)、交通(tra)等；
- `feature` 可选，表示样例的功能用途，强烈建议增加，可以是1个单词或多个单词，多个单词之间使用中划线连接，要求简短、好记、具备辨识度；
- 统一采用 `-samples` 后缀。

**示例**：

| 仓库名 | 含义 |
|--------|------|
| `elec-ops-simulation-samples` | 电力仿真求解算子样例仓 |

### 7.3 Sample 与 Recipe 的区分

| 维度 | Sample | Recipe |
|------|--------|--------|
| 目的 | 演示单一功能/API | 端到端可复现流程 |
| 完整度 | 片段式，可独立运行 | 全流程（数据→训练→推理→评测） |
| 受众 | 初学者 | 进阶用户 |

## 8. 工具仓命名

**命名格式**：

```
<feature>-tools | <feature>-toolkit | <feature>-devkit
```

- `feature` 表示工具的功能用途，必选，可以是1个单词或多个单词，多个单词之间使用中划线连接，要求简短、好记、具备辨识度；

- 采用 `-tools` 、 `-toolkit` 、 `-devkit` 后缀，其中tools表示独立工具，toolkit表示完成特定任务提供的工具箱，devkit表示面向开发者的开发套件。

  选择规则：

  - 单一可执行工具 / 命令行小工具集 → `-tools`（如调试工具、转换工具）
  - 完成特定任务的多工具组合包 → `-toolkit`（如编译工具链包）
  - 面向开发者的完整开发套件（含 SDK + 文档 + 示例 + 调试） → `-devkit`

**示例**：

| 仓库名 | 含义 |
|--------|------|
| `asc-tools` | Ascend C编程调试工具仓 |
| `asc-devkit` | Ascend C编程语言开发套件仓 |
