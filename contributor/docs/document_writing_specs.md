## 概述

本文档针对CANN组织下开源项目的**Markdown格式文档**制定了统一的写作规范，涵盖了内容、目录、元素和质量合规要求，旨在确保所有文档风格一致、结构清晰、易于使用。

开发者在进行CANN文档写作前，请务必阅读并遵循本规范。欢迎随时提出改进建议。

写作过程中请采用符合业界标准的Markdown语法写作，如无特殊要求不推荐使用HTML语法。

## 文档结构规范

### 文档内容要求

#### 必选内容

每个开源项目需要包含如下核心内容，标题可以根据项目特点微调：

- 概述：介绍项目的功能、架构与关键特性。
- 编译安装：提供完整的源码编译与构建指南。
- 本地验证：指导如何通过简单样例验证基础功能。
- 贡献指南：说明如何参与项目贡献。
- 许可证：声明项目遵循的开源许可协议。

#### 可选内容

各开源项目可以根据实际情况补充如下内容（包括但不限于）：

- 样例使用指导：examples的功能说明、编译执行步骤与结果示例等。
- 参考文档：相关产品文档、培训视频等资源的链接。
- 定制开发指导：基于项目源码进行二次开发的指南等。
- API参考：开放的接口说明。

### 目录结构规范

- 总体原则

  【规则】单一项目的多个工具/组件文档，应统一存放于`docs`目录下，并按子目录分类管理。

  【规则】`docs`目录下区分`zh`（中文）与`en`（英文）子目录。

  【规则】若文档数量较少（如单个算子），可不区分`zh/en`目录，采用文件后缀区分：英文文件加`_en`后缀，中文文件无后缀，例如：`aclnnAbs.md`与`aclnnAbs_en.md`。

  【规则】与代码强关联的文档（如examples、算子说明），直接归档在对应代码目录下。

- API文档目录规划

  【规则】每个API或每个类对应一个markdown文件，单个项目规划保持统一。

  【规则】API文档必须提供目录索引文件（如`README.md`或`xx_list.md`，名字可自定义）。API数量多时，索引文件应置于API文件的上层目录。

  【规则】若API按框架、组件、语言等分类，须通过子目录区分。

  目录结构示例：

  ```text
  # 示例1：平铺结构（文档较少）
  |-- xx_list.md
  |-- api1.md
  |-- api2.md
  |-- api3.md

  示例2：索引文件外提
  |-- xx_list.md
  |-- context
  |--|-- api1.md
  |--|-- api2.md
  |--|-- api3.md
  |--|-- ...

  示例3：多语言API
  |-- c_api
  |--|-- c_list.md
  |--|-- context
  |--|--|-- api1.md
  |--|--|-- api2.md
  |--|--|-- ...
  |-- python_api
  |--|-- python_list.md
  |--|-- context
  |--|--|-- api1.md
  |--|--|-- api2.md
  |--|--|-- ...

  示例4：统一索引，按功能特性分组
  |-- api_list.md
  |--|-- feature1
  |--|--|-- api1.md
  |--|--|-- api2.md
  |--|--|-- api3.md
  |--|-- feature2
  |--|--|-- api1.md
  |--|--|-- api2.md
  |--|--|-- api3.md
  |--|-- feature3
  |--|--|-- api1.md
  |--|--|-- api2.md
  |--|--|-- api3.md
  ```

### 文件命名规范

对于新增文档，请在对应的文件目录下新增Markdown文档（即以`.md`结尾的文件）。

【规则】文件名须以英文字母、数字或英文符号命名，符号建议使用下划线（_）或中划线（-），其他符号不推荐使用。

【规则】文件名不宜过长，建议不超过70个字符，推荐50个字符以内。

【规则】README文档：中文命名为`README.md`，英文命名为`README_en.md`。

【规则】同一目录下不能出现重名文件。

### 文件编码格式要求

Markdown文件需要使用UTF-8编码格式，此编码格式支持所有语言字符，且跨平台兼容性好。

不可使用UTF-8 with BOM的编码格式，此格式会在文件开头添加3个冗余字符：EF BB BF，可能会造成不同平台上的显示异常问题。

## 内容元素规范

### 标题

【规则】标题应简洁明了，概括章节核心内容。

【规则】操作类标题使用动宾结构（例如“申请权限”）；同级别同类型标题结构保持一致。

【规则】标题末尾不加标点，避免使用特殊字符（如“?”），补充说明使用圆括号。

【规则】标题与正文间空一行。

【规则】标题使用 `#[空格][标题名]`，标题级别需逐级递增，第一个标题应该是顶层标题。

【规则】标题中不能手工添加序号，例如 “## 1. 安装CANN”，需要修改为 “## 安装CANN”。

【规则】标题建议最多四级。

【示例】

```markdown
# 一级标题
## 二级标题
### 三级标题
#### 四级标题
```

### 字体样式

【字体样式】

- 斜体：使用一个星号（\*）表示斜体。

    ```txt
    *斜体文本*
    ```

- 粗体：使用两个星号（\*\*）表示粗体。

    ```txt
    **粗体文本**
    ```

- 粗斜体：使用3个星号（\*\*\*）表示粗斜体。

    ```txt
    ***粗斜体文本***
    ```

- 转义：对特定内容使用转义符 \。

    ```txt
    \<转义的标记符号\>
    ```

### 图片

【规则】图片需要以英文字母命名，多个单词以下划线（_）或中划线（-）连接，名称不宜过长，建议不超过50个字符。

【规则】图片统一存放到文档同级目录下的 **figures** 文件夹中，使用相对路径引用。

【规则】请使用原创图片，避免侵权。

【规则】图文配合使用，切忌图文分离。

【规则】图片格式支持PNG、JPG、SVG，以及Mermaid语法图。

【规则】中/英文文档须分别使用对应语言的插图。

【规则】截图应只保留核心内容，关键信息可用红框或文字标注。

【规则】确保图片清晰可辨。

【规则】PNG、JPG二进制图片上传到仓库时请使用git lfs托管。

【图片插入格式】

```markdown
![alt属性文本](图片地址)

![alt属性文本](图片地址 "可选标题")

# 示例
![](./figures/ci_check_result.png)
或
![](figures/ci_check_result.png)
```

### 代码块

【规则】确保代码的逻辑和语法正确。

【规则】清晰区分输入与输出部分。

【规则】关键步骤须有注释说明。

【规则】文中行内代码和命令行使用1对反引号，如： `行内代码`。

【规则】块级代码使用3个反引号，并声明语言类型，上下空一行。常见语言类型包括：python、c、c++、markdown、bash、ini、yaml、json、xml、html、java、javascript、php、sql、ruby等。

【示例】

- 行内代码

  ```txt
  `printf()` 函数
  ```

- 块级代码

  ```c
  #include  <stdio.h>
  int main(void)
  {
      printf("Hello world\n");
  }
  ```

  ```python
  #!/usr/bin/env python3
  print("Hello, World!");
  ```

  输出：

  ```text
  Hello, World!
  ```

### 列表

【规则】有明显先后逻辑顺序情况请使用有序列表，并列关系、多选一情况请使用无序列表。

【规则】当项目列表是术语、短语时，统一不加标点符号；为完整句子时，统一加句号；混合情况下，统一加句号。

【规则】项目列表前几项以分号结尾，最后一项以句号结尾的形式也可以接受。

- 无序列表：无序列表使用星号（**\***）、加号（**+**）或是减号（**-**）作为列表标记，这些标记后面要添加一个空格，然后再填写内容。一个文件中的同一个无序列表，建议使用同一个符号。

    ```txt
    * 第一项
    * 第二项
    * 第三项

    + 第一项
    + 第二项
    + 第三项


    - 第一项
    - 第二项
    - 第三项
    ```

- 有序列表：有序列表使用数字并加上  **.**  号来表示，不支持使用字母（例如a b c）作为序号。

    ```txt
    1. 第一项
    2. 第二项
    3. 第三项
    ```

- 嵌套列表：列表嵌套只需在子列表中的选项前面添加两个或四个空格（不要使用tab键）即可。

    ```txt
    1. 第一项：
        - 第一项嵌套的第一个元素
        - 第一项嵌套的第二个元素
    2. 第二项：
       - 第二项嵌套的第一个元素
       - 第二项嵌套的第二个元素

    - 第一项：
      - 第一项嵌套的第一个元素
      - 第一项嵌套的第二个元素
    - 第二项：
      - 第二项嵌套的第一个元素
      - 第二项嵌套的第二个元素
    ```

### 引用块

文档支持以引用块方式补充对正文的描述，描述可以按重要程度区分，具体如下。

- 说明：提供辅助性提示或参考信息。

  ```text
  > [!NOTE]说明
  > 正文
  ```

- 注意：如未按此操作，可能导致任务中断或结果异常（可恢复）。

  ```text
  > [!CAUTION]注意
  > 正文
  ```

- 警告：如不避免，可能导致轻微或中度伤害。

  ```text
  > [!WARNING]警告
  > 正文
  ```

写作要点：

- 请根据使用场景选择恰当的引用块。
- 引用块可嵌套有序/无序列表，但不建议表格和代码块。
- 使用连续的`>`符号以保证样式不中断。
- 说明/注意等样式中内容应简洁，过长可考虑迁移至正文或者分段处理。

### 链接

【规则】确保链接真实存在并且安全有效，避免虚假链接。

【规则】仓内链接建议使用相对链接，仓间链接使用绝对链接。

【规则】引用文档时建议用书名号包裹并添加超链接。

【示例】

```markdown
- 网站链接
  AA的安装步骤请参考[“安装与部署”](https://www.aa.com)。

- 相对路径
  [文档开发流水线门禁](./ci_rules.md)
```

【规则】引用文档内标题、图片或表格时，请使用锚点。

**锚点设置方法：**

  方法一：将标题中大写字母转换为小写，空格替换为中划线`-`，并去除特殊符号。

  方法二：添加\<a\>标签，在\<a\>标签中自定义锚点ID。

【示例】

```markdown
# 安装前准备 A*

这是CANN的安装前准备。

...

参考[安装前准备](#安装前准备-a)章节。


**图1** CI检查结果
![CI检查结果](./figures/ci_check_result.png)<a id="fig11"></a>

```

### HTML标签

【规则】非必要不推荐使用复杂HTML标签，例如复杂的CSS样式等。

【规则】若文档使用了HTML语法，请确保需要闭合的标签成对出现并正确闭合；`<br>`、`<hr>`、`<img>`、`<input>`等空元素除外。

【反例】

```text
  <table>
    <tr>
      <th>Header 1
      <th>Header 2</th>   <!-- 错误1：未闭合的<th> -->
    <tr>                  <!-- 错误2：未闭合的<tr> -->
      <td>Data 1<td>      <!-- 错误3：自闭合<td> -->
      <td>Data 2</td>
  </table>                <!-- 错误4：未闭合的<tr>导致结构错乱 -->
```

### 表格

【规则】使用标准Markdown表格语法，若无特殊格式诉求不建议使用HTML表格。

【规则】表格列数不能超过9列。

【规则】当表格内一列全部是术语、短语时，统一不加标点符号；为句子时，统一加句号；混合情况下统一加句号。

【规则】无论markdown表格或HTML表格，不允许存在空白单元格。

【示例】

| 表头1 | 表头2 |
| -------- | -------- |
| 单元格1 | 单元格2 |
| 单元格4 | 单元格4 |

【使用方法】

设置表格的对齐方式：

- --: 设置内容和标题栏居右对齐。
- :-- 设置内容和标题栏居左对齐。
- :--: 设置内容和标题栏居中对齐。

### 公式

【规则】使用LaTeX语法公式。

【规则】行内公式，前后使用`$`包裹。

【规则】块级公式，前后使用`$$`包裹，且`$$`单独成行。

行内公式示例：

```text
方程$ax^2+bx+c=0$有两个根。

```

块级公式示例：

```text
$$
\int_{-\infty}^{+\infty} e^{-x^2}\,dx = \sqrt{\pi}
$$
```

## 文字表述规范

### 语言风格规范

【规则】避免使用口语化表达，保障文档专业性、可读性。【反例】：不准、so easy。

【规则】内容要求易理解、无歧义，不存在语病（例如缺少主语、语序混乱、断句不正确等）。

【规则】减少使用复杂结构的长语句表达，推荐精简的短语句。

【规则】避免前后文重复描述、表述拖沓冗长（例如同义词堆叠、修饰词冗余、重复主语/谓语、解释过度等）。

【规则】避免前后文语义不一致甚至语义矛盾。

【规则】章节要求层次清晰，逻辑合理。

### 术语

【规则】使用术语、专有名词时，大小写请使用符合业界通用常识的表达，请勿自定义。

【规则】CANN产业术语要求：参考[昇腾术语表](https://www.hiascend.com/document/detail/zh/Glossary/gls/gls_0001.html)的表达，避免使用变体表达。如术语表中为AI Core，禁止使用aicore。

【规则】术语首次在正文出现时，必须提供全称和详细的解释，尤其是缩写词。例如“Open Build Service”而不是直接抛出“OBS”。

### 空格

文档中不允许出现多余空格，中英文混排场景，遵循中文习惯。

【规则】数值和单位、中文与英文、中文与数字之间均不加空格。例如：50m，10kg，昇腾AI处理器，36ºC。

【规则】“=”、“~”、“<”、“>”、“≥”和“≤”符号前后加空格。例如：1Byte = 8bit。

【规则】键盘组合快捷键在文本中出现时，“+”前后不留空格。例如：Ctrl+S。

【规则】代码应按语言约定进行缩进与对齐（如Python使用4个空格，Java使用4个空格或1个Tab），且同一代码块内的缩进须保持一致。

> [!NOTE]说明
>
> - 通过编辑器写作MarkDown文档时，可以使用插件支持的空格规范检查工具检查，开启自动格式化功能。例如VS Code安装“Prettier”插件，配置 “禁止连续空格”“自动删除行尾空格”。
> - 对代码示例使用对应语言的Lint工具（如Python用pylint，Java用Checkstyle），确保空格符合语法规范。

### 标点符号

【规则】文档中不允许出现多余的标点符号。不支持连续两个及以上标点符号（成对标点符号后接结尾符号的场景除外）。

【规则】文档中不能缺少必须的标点符号。对于文档中的章节、有序/无序列表、表格、引用块等元素，句子末尾通常要加句号或其他标点表示内容的结束。

【规则】中文行文中的标点遵循中文全角规范；但凡是具有语法或语义结构的符号串（取值范围、shape、数学式、代码、路径、URL等），应整体保持其半角格式，不按中文标点规则转换。例如，取值范围：(0, 100)、[0, 1]；数据shape：(2, 3, 4)、(batch, seq_len, dim)。

【规则】双引号、圆括号、方括号、大括号需要成对出现。以下场景除外：

  - 字符串中使用半边小括号作为编号格式。
  - 回显里面的标点符号不成对。
  - 取值范围混用小括号和中括号，例如“[3, 6)、(0,3]”。

【规则】路径表达方式按操作系统区分：

  - Windows操作系统的路径表达方式为`"drive name:\folder 1\folder 2\folder 3..."`。
  - UNIX操作系统的路径表示方式为`"$ROOT/etc/conf/"`。
  - Web中路径的表达方式为`"http://www.huawei.com"`。
  - Mac操作系统路径表达方式为`"/folder 1/folder 2"`。

【规则】特殊标点使用规范：

  - 感叹号：仅用于可能引发严重人身或设备安全后果的警告。
  - 书名号：引用产品手册或书籍时推荐增加书名号，如有链接请同步增加。例如：参考《[CANN软件安装](https://www.hiascend.com/document/detail/zh/CANNCommunityEdition/latest/softwareinst/instg/instg_0000.html?OS=openEuler&InstallType=netyum)》。

### 单位符号

【规则】计量单位符号全称或缩写（例如：毫米缩写mm）必须符合国际单位制（SI）通用标准，请勿自定义。

【规则】避免中文单位和英文单位混用。【反例1-语义重复：长度不超过10米m】、【反例2-语义矛盾：角度不超过10度mm】

【规则】文档中同一种数值单位的写法前后文保持一致。

【规则】缩写的单位符号不随数值变为复数，例如物理类单位（m、kg、s等）。例如10 Bytes、10B（缩写）。

### 中文错别字

- 【规则】避免出现形近字错误，例如“己/已/巳”、“阈值/阀值”、“好像/好象”。

- 【规则】避免出现音近字错误，例如“需/须”、“部署/布署”、“型号/形号”、“其他/其它”、“登录/登陆”。

- 【规则】避免漏字、多字或重复字的情况，例如“点击确定按钮”是否漏写“按”字、“系统将将重启”是否多写“将”字。

### 产品标签使用规范

对于产品文档，当存在产品差异时，需通过HTML注释标签隔离不同产品的差异，便于在发布时实现**按产品过滤**能力，即仅保留目标产品标签块内的内容与未打标内容。

格式为：

  ```html
  <!-- npu="950" id1 -->
  对于Ascend 950PR&950DT系列产品，支持的数据类型为DT_FP16，DT_BF16，DT_FP32。
  <!-- end id1 -->
  ```

  使用要求：

- id：必填，要求文件内唯一。
- npu：必填，取值及对应的产品含义如下。支持多个取值，多个取值间使用英文逗号分隔。

  - 950：Ascend 950PR&950DT系列产品
  - A3：Atlas A3系列产品
  - 910b：Atlas A2系列产品
  - 310b：Atlas 200I/500 A2推理产品
  - 310p：Atlas推理系列产品
  - 910：Atlas训练系列产品
  - IPV350：IPV350
  - 5162A：Hisilicon5162A
  - x90：KirinX90处理器系列产品
  - 9020：Kirin9020处理器系列产品
  - 9030：Kirin9030处理器系列产品
  - 9050：Kirin9050处理器系列产品
  - kirin1：KirinDev0001处理器系列产品
  - kirin2：KirinDev0002处理器系列产品
  - kirin3：KirinDev0003处理器系列产品

- 支持产品标签嵌套场景，例如：

    ```html
    <!-- npu="950,A3" id2 -->
    xxx
    <!-- npu="950" id3 -->
    xxx1
    <!-- end id3 -->
    <!-- npu="A3" id4 -->
    xxx2
    <!-- end id4 -->
    <!-- end id2 -->
    ```
